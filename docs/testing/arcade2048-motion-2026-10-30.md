# 2048 GPU tile motion and stable footer

Human follow-up: lateral tile movement looked blurry/juddery, and the footer kept changing while saves ran. The active footer is now exactly **“Use WASD or mouse to move them”**, independent of pending/idle state. Local/ranked clarity remains in the world/proximity/records UI.

Tested runtime: `bbf9e22a8a16613cf07b13f9b317e1f693588cb1`, including accepted main `f695e30`. The implementation commit is `0c348aa`. PR43 was subsequently merged as main `4eee676`; the release owner verified that main's tree matched the tested candidate. This report adds proof only, not runtime changes.

## Rendering change

The previous code repainted a 768×960 CanvasTexture while animating and explicitly capped these updates at 30Hz. That was a display bottleneck even when the surrounding world rendered faster. The new renderer caches the existing tile artwork in one 1536×768 atlas (about 4.5MiB RGBA at base level, no mipmaps), then moves at most 16 GPU instances using small transform buffers at the renderer's cadence. It adds one instanced tile draw per render pass and at most 32 tile triangles. The actual GLB's UV corners define the layer's matrix; a half-texel inset and clipped atlas cells prevent neighboring-cell bleed.

The base canvas paints the shell/header/footer and rare modal/error/records states. It updates on visual state changes, without repainting for each interpolation frame or pending-save toggle. The decorative GPU layer does not raycast, so the actual screen remains the mouse target. Modal/error states hide that layer and use the existing Canvas board fallback. Reduced motion supplies the final static tile positions. A tested retain/release lifetime keeps resources live through StrictMode effect replay and disposes only after final ownership ends.

## Actual-world measurements

The sole preview owner granted an additive window on the existing 4173 listener, with the normal 262-file build preserved. One owned browser tab ran the actual Game, decoded GLB, compiled shader, physics controller and local SharedWorker. Hardware was Apple M4 Pro (14 logical CPU cores, 48 GiB memory), macOS 26.5.2, using the Codex in-app browser. The page was visible at CSS 1707×960 and DPR 1.5; `prefers-reduced-motion` was false. These are render-frame measurements from this setup, not a promise of presented-frame FPS on all hardware.

| Measurement | Same-world idle baseline | During repeated moves |
| --- | --- | --- |
| Median R3F frame interval | 8.3ms | 8.3ms |
| P95 R3F frame interval | 10.2ms | about 9.9–10.3ms |
| Cabinet update CPU P95 | about 0.1ms | about 0.1ms |

The observed median corresponds to about 120 render frames/second. This compares idle and moving states in the same scene and fixed cabinet camera. It is not an old-bundle CPU/GPU benchmark; the earlier 30Hz ceiling is established by the previous source.

Across 16 accepted moves:

- Base-screen upload requests and actual Three texture-update callbacks increased from 3 to 19: exactly 16 state updates, rather than repeated whole-screen updates throughout each slide.
- Atlas redraw requests stayed at 2 and actual texture-update callbacks stayed at 1: no additional atlas upload during movement. The initial font refresh coalesced before first GPU use.
- Small instance-buffer updates increased from 2 to 306: 304 updates across the movement/merge/spawn transitions.
- The shader produced no captured console errors. Tile values, colors, orientation, alignment, rounded edges and font shape matched the board; no atlas bleed was observed.

Counters are sampled every 500ms. The final settled counter snapshot is used for the 16-move delta rather than a potentially lagging last-input sample. `tileRenderCalls` counts `onBeforeRender` callbacks, including reflected scene passes; it is not a presented-frame counter. The reported single-draw field is the instanced layer's configured per-pass draw budget. Literal data: [metrics.json](captures/arcade2048-motion/metrics.json).
