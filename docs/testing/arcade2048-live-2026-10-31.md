# Live cabinet display and personal save reconciliation

User report: a friend was actively playing, both clients were on production and refreshed, yet the physical screen appeared unchanged or different. Personal saves must remain independent while each occupied cabinet shows its current player.

## Reproduced on current runtime

Frozen diagnostic `37be90b` uses the actual Game, model, physics, room and in-memory SharedWorker. Observation-only aliases call the original canvas painter and tile factory; they capture text actually painted and reconstruct the real instance-buffer faces/positions on draw callbacks. Normal production entry points do not import these probes. No performance measurements are inferred under concurrent authoring load.

- Normal path works: the owner's score 24 board matches the spectator's real canvas text and GPU tile payload, including after the spectator has a different saved personal game. See [normal-path.json](captures/arcade2048-live-2026-10-31/normal-path.json).
- Cross-click mismatch: a player standing at middle station 1 can click nearby station 2. The camera/claim move to 2, but the avatar stays at 1. The spectator sees the idle attract board at the avatar's apparent cabinet while 2 correctly shows the active score 36 game. See [cross-click.json](captures/arcade2048-live-2026-10-31/cross-click.json) and [capture](captures/arcade2048-live-2026-10-31/cross-click-spectator.jpg).
- Stale authority display: after an authored walk-away causes the real server to release A's claim 2, A's UI remains active. B claims 2 with a different saved board. A receives B's correct public DTO but its actual canvas/GPU still draws A's old score 36 board and Leave controls. See [literal draw mismatch](captures/arcade2048-live-2026-10-31/lost-claim-stale-display.json) and [capture](captures/arcade2048-live-2026-10-31/lost-claim-stale-display.jpg).
- A can subsequently resume the exact score 36/11-move personal game at station 0; the save was never overwritten. See [diagnosis.json](captures/arcade2048-live-2026-10-31/diagnosis.json).

These are reproduced failure modes, not a claim that the exact trigger in the user's earlier production session has been established. A separate anonymous production snapshot found no active players at that instant and was therefore inconclusive for the reported active case.

Both diagnostic clients left and closed; six additions were removed and the entire 293-file name/SHA/size manifest was restored at 10:17:42 UTC. [Restoration](captures/arcade2048-live-2026-10-31/restoration.json).

## Correction

The public station owner now determines which physical display may use local controls/private view. Loss of ownership disables actions and turns the physical screen into the current occupant's public view immediately; stable online claim loss also closes the old controller. A new connection identity gets its restore opportunity before an empty snapshot is treated as a release. The personal game remains saved separately, and legacy single-cabinet behavior is retained.

After a successful current-generation claim and matching public ownership, the local character aligns once to the chosen numbered cabinet's authored 1.2 m standing pad and faces its screen. Failed, cancelled, stale and unowned entries do not provide a placement request. The handler follows existing ground/standing conventions and leaves generic movement, vehicle, jump and seat paths intact.

Checks before confirmation: 507 frontend tests/85 files and 171 protocol/backend tests/12 files pass, both TypeScript checks, production build and Worker dry run pass. The compiled Worker JavaScript is byte-identical to the pre-change bundle (`3b6b5df6e8a14818b4f0cad32cc65b274451546691f5327c3688cfedb9be29bc` in this checkout); no backend deployment, save migration, budget change or new static assets are needed. Independent source reviews found no blocker. Fixed-candidate actual-Game confirmation and publication remain pending.
